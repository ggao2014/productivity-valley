# Productivity Valley 路线图

> 状态：Draft v1  
> 路线图起点：v0.4 原型  
> 产品原则：先让“完成现实待办 → 山谷产生变化 → 想再回来”成立，再扩充内容和系统。

## 1. 当前判断

项目已经具备可运行的 Web/PWA 原型，规则层包含：

- 待办的新增、完成、删除与三档难度奖励
- 金币、精力、礼物和房间经济
- NPC 相遇、友情/爱情、互动次数与送礼
- 邀请入住、分开住、每日维护与欠费提示
- 本地存档和 GitHub Pages 构建配置

但距离可验证的 MVP 还有四个主要差距：

1. **缺少首次体验**：玩家进入后不知道目标、规则和下一步。
2. **缺少内容密度**：角色虽有数据，但对话、事件和个性不足以让人记住。
3. **缺少成长表现**：完成待办后，山谷的视觉变化和持续目标不够强。
4. **缺少产品保障**：没有自动化测试、存档迁移、错误恢复和正式反馈渠道。

因此，近期不优先增加更多系统，而是补齐一个完整、好懂、可重复的核心循环。

## 2. 美术生产与实现方式

美术不作为开发完成后的“包装”，而是随每个功能一起设计、生成、接入和验收。每批素材遵循同一流程：

1. **写素材 Brief**：说明用途、画面内容、尺寸、透明区域和交互状态。
2. **生成风格候选**：每个关键主体先生成少量方向稿，不直接批量扩图。
3. **锁定参考图**：选择一张作为后续同类素材的构图、比例、服装和笔触参考。
4. **生成正式素材**：基于参考图制作表情、动作、状态或场景变体。
5. **规范化处理**：统一裁切、分辨率、透明背景、色彩空间和文件命名。
6. **接入真实界面**：不脱离应用单独判断，必须在手机和 iPad 布局中检查。
7. **视觉 QA**：检查辨识度、一致性、点击区域、文字对比度和资源体积。

### 2.1 统一视觉基准

在批量生成任何素材前，先锁定一份视觉圣经：

- **画风**：柔和水彩 + 彩色铅笔，暖纸纹理，棕色墨线
- **主色**：苔藓绿、暖纸色、陶土橙、墨线棕
- **点缀色**：月白、靛青、胭脂
- **角色比例**：大头短身，中式绘本小人，轮廓清楚
- **辨识方式**：道具、服色和体态优先，不依赖复杂五官
- **避免方向**：霓虹紫、仙侠金光、写实厚涂、3D 塑料感、现代网红渐变
- **界面原则**：场景插画负责情绪，SVG 图标负责清晰交互

视觉圣经至少包含：

- 一张山谷风格基准图
- 一张小屋与房间结构基准图
- 三名核心角色的标准设定图
- 固定色板和纸张纹理
- 正确/错误示例
- 图像生成母 Prompt、负面 Prompt 和各类素材模板

### 2.2 素材技术规范

建议目录：

```text
public/art/
  environment/      # 山谷、天空、路径、前景
  house/            # 小屋主体、房间模块、门窗状态
  characters/       # 每名角色的立绘、头像、表情、小人
  rooms/            # 房间内部和可叠加物件
  gifts/            # 礼物图标
  effects/          # 金币、精力、亮灯等关键帧
  empty-states/     # 空状态插画
src/assets/icons/   # 代码维护的 SVG UI 图标
```

规范：

- 固定背景优先使用 WebP
- 透明角色和物件优先使用透明 WebP，必要时保留 PNG 源文件
- UI 图标使用 SVG
- 原始生成图与应用压缩图分开保存
- 文件名使用英文小写与短横线，如 `guwan-portrait-shy.webp`
- 每张图记录用途、来源 Prompt、参考图和版本
- 首屏图像提供响应式尺寸，避免直接加载超大原图
- 不把文字画进插画，文案由 HTML 渲染

### 2.3 美术完成定义

一项视觉功能只有满足以下条件才算完成：

- 素材已进入正确目录并有稳定命名
- 在真实页面中完成接入
- 手机、iPad 和桌面均检查过裁切
- 角色道具、服色和体态与设定一致
- 透明边缘无明显白边或脏像素
- 页面加载体积和清晰度达到可接受平衡
- 提供替代文本或等价的无障碍信息

## 3. 版本路线

## Phase 0 — 稳固原型（v0.5）

**目标：** 让当前版本可以安全地持续开发，同时锁定一套可批量扩展的视觉语言。

预计周期：1 周

### 产品与技术

- 为 `core/` 补充单元测试
  - 三档待办奖励
  - 房间购买与容量
  - 友情/爱情阶段升级
  - 每日互动上限
  - 邀请、分开住和维护费
- 为存档增加 `schemaVersion` 和迁移入口
- 增加“导出存档 / 导入存档”
- 增加错误边界与损坏存档恢复
- 检查并处理依赖安全警告
- 建立基础 CI：lint、typecheck、test、build
- 为核心数值建立一份可读的平衡表

### 美术生产

- 建立视觉圣经 v1
- 制作 2–3 个山谷风格方向稿
- 选定并固化一张山谷风格基准图
- 设计沈渡、顾晚、桃桃三名核心角色的轮廓草案
- 锁定角色头身比、线条粗细和固定色板
- 建立素材目录、命名规则、压缩脚本和素材登记表
- 用新的 SVG 替换项目中与产品无关的社交平台示例图标

### 完成标准

- 核心规则测试全部通过
- 旧存档升级后仍可打开
- 损坏存档不会让应用白屏
- 每次 PR 自动执行质量检查
- `npm audit` 中的生产依赖无高危漏洞，或有明确的风险记录
- 山谷与三名角色属于同一个清晰可辨的视觉世界
- 后续角色和场景可以复用已锁定的 Prompt 与参考图
- 一张测试角色图已接入当前山谷页面，验证清晰度和比例

## Phase 1 — 完整核心循环（v0.6）

**目标：** 新玩家在 10 分钟内自然完成一次“待办 → 奖励 → 互动 → 成长”循环。

预计周期：2 周

### 产品与技术

- 轻量首次引导
  1. 写下第一个待办
  2. 完成待办并获得金币、精力
  3. 与第一个角色互动
  4. 看见下一项成长目标
- 今日进度区
  - 今日完成数量
  - 今日获得金币/精力
  - 连续活跃天数
- 明确所有锁定条件和下一步提示
  - 为什么不能买房
  - 为什么不能继续互动
  - 如何解锁爱情线
  - 如何邀请入住
- 强化完成反馈
  - 奖励飞入余额
  - 小屋亮灯或生长动画
  - NPC 对完成待办作出短回应
- 增加任务编辑和撤销误完成
- 改善空状态、加载状态和触屏交互

### 美术生产

- 将山谷基准图拆成可交互图层：
  - 天空与远山
  - 草地
  - 小路
  - 树木与灌木
  - 小屋
  - 前景花草
- 制作小屋基础状态、门开/关和窗户明/暗状态
- 制作沈渡、顾晚、桃桃的山谷小人
- 为其他已出现角色制作临时剪影，避免姓名圆圈占位
- 制作首次引导所需的 3–4 幅小型提示插画
- 制作金币、精力、完成、编辑、删除等第一批 SVG 图标
- 制作“金币与精力落下”“窗户亮起”的动效素材
- 为没有待办、还没遇见角色制作空状态插画

### 完成标准

- 首次玩家无需阅读设计文档即可完成核心循环
- 任一禁用操作都能解释原因
- 完成待办后 1 秒内出现清晰的视觉与数值反馈
- iPad 与手机尺寸下，主要操作无需缩放且无横向溢出
- 山谷背景、角色和点击热区在三种屏幕尺寸下正确对齐
- 完成待办后，插画场景会产生一次明确但不过度的变化
- 首屏压缩后资源体积满足既定性能预算

## Phase 2 — 让角色值得记住（v0.7）

**目标：** 用少而精的内容验证“生产力乙游”是否真的有情感吸引力。

**实施状态（2026-07-30）：** 产品、技术、内容与美术实现已完成；真实测试玩家能否仅凭对话辨认三名角色，留待 Phase 4 封闭测试取证。逐项证据见 `docs/PHASE2_AUDIT.md`。

预计周期：3–4 周

### 范围策略

先精做 **3 名核心角色**，不要同时摊开 12 人。三人的性格、说话节奏、偏好和关系体验必须明显不同；验证通过后再扩展角色池。

### 产品与技术

- 每名核心角色具备：
  - 清晰的人设、声口和视觉轮廓
  - 20–30 条日常对话
  - 3 个友情事件
  - 3 个爱情事件
  - 喜爱、普通、讨厌礼物反馈
  - 入住前后不同的对话
- 对话系统支持：
  - 条件触发
  - 已读状态
  - 关系阶段
  - 时间/房间/入住条件
- 事件回顾册
- 角色档案与已发现喜好
- 内容数据与 React 组件分离，便于持续写作

### 美术生产

为沈渡、顾晚、桃桃分别制作：

- 标准全身立绘 1 张
- 对话半身像 1 张
- 平静、开心、担心、生气、害羞 5 个表情状态
- 山谷正面小人 1 张
- 背面/行走姿态 1 张
- 提着小包的搬入状态 1 张
- 友情事件插画 1 张
- 爱情事件插画 1 张
- 专属道具图标 1 枚

同时：

- 制作角色档案页的纸张边框与关系隐喻
- 制作“两杯茶”和“小灯”关系阶段 SVG
- 制作 12 种礼物图标
- 为每张角色图建立参考图链和一致性检查表
- 将身体、表情和道具尽量拆层复用，避免重复生成整张图

### 完成标准

- 测试玩家能仅凭对话辨认三名角色
- 每名角色至少有一条从相遇到入住的完整内容路径
- 重复游玩一周时，不频繁出现相同对话
- 新增对话或角色不需要修改规则引擎
- 同一角色在立绘、头像、小人和事件图中保持服装、发型、道具和配色一致
- 三名角色缩小到山谷尺寸后仍能仅凭轮廓和主色区分
- 表情切换不会产生明显的脸型和服装漂移

## Phase 3 — 山谷成长与长期目标（v0.8）

**目标：** 让现实中的努力在山谷里留下持续、可见的痕迹。

预计周期：3 周

> 实施进度（2026-07-30）：成长规则、四张阶段背景、下一目标、温和周目标与上周小结、6 类图像化里程碑、12 件可收藏/摆放装饰、v8 存档迁移均已接入；厨房、书房和储藏室现已分别影响维护、任务奖励和礼物容量。剩余工作集中在搬入的开门/窗边剪影状态、阶段环境微动效与 Phase 3 完成审计。

### 产品与技术

- 山谷视觉分阶段成长
  - 荒地
  - 初步修整
  - 温暖小屋
  - 有人生活的家
- 房间从“购买列表”升级为可见空间
- 房间功能深化
  - 厨房降低维护
  - 书房强化中/大任务奖励
  - 储藏室扩充礼物容量
- 装饰系统第一批：10–15 件装饰
- 每周目标与温和总结
- 里程碑系统
  - 完成任务数
  - 首次购买房间
  - 首位好友
  - 首位伴侣入住
- 避免惩罚性连续签到；中断后可自然继续

### 美术生产

- 制作山谷四阶段成长状态
  - 荒地
  - 初步修整
  - 温暖小屋
  - 有人生活的家
- 制作可拼贴的小屋扩建模块
  - 卧室
  - 厨房
  - 书房
  - 客房
- 制作五个房间的室内基础插画
- 制作 10–15 件首批装饰
- 制作房间落成的纸片展开关键帧
- 制作伴侣搬入的走路、开门和窗边剪影状态
- 制作里程碑小插画和每周总结装饰
- 制作轻量烟雾、叶片、灯光等环境动效；避免持续抢夺注意力

### 完成标准

- 玩家能从山谷画面判断大致成长阶段
- 至少三种房间会改变玩家决策，而不只是收藏
- 玩家连续使用 7 天后仍有清晰的下一目标
- 没有必须刷取或强制每日登录的机制
- 房间模块拼接时透视、光向和纸张质感一致
- 山谷升级不会导致原有角色点击位置错位
- 动效开启与“减少动态效果”模式下都可正常使用

## Phase 4 — 封闭测试版（v0.9）

**目标：** 验证留存、理解度和情感吸引力，决定是否进入 1.0。

预计周期：2 周开发 + 2–4 周测试

> 工程进度（2026-07-30）：v0.9 邀请入口、本机匿名事件与隐私开关、反馈导出、测试指标汇总脚本、安装指引、离线/更新状态、自有 Service Worker、状态插画、键盘与屏幕阅读器基线均已接入。自动门禁通过且依赖审计为 0 漏洞。2–4 周真实测试与决策门数据尚未开始，不能以仓库内测试替代。

### 产品与技术

- 邀请制测试入口
- 匿名产品事件
  - 完成首次待办
  - 完成核心循环
  - 解锁友情/爱情阶段
  - 购买房间
  - 次日/第七日返回
- 应用内反馈入口
- 隐私说明与数据开关
- 安装 PWA 引导
- 离线、更新和新版本提示
- 无障碍检查
  - 键盘操作
  - 对比度
  - 减少动态效果
  - 屏幕阅读器标签
- 发布检查清单和回归测试

### 美术生产

- 对全套已接入素材进行统一性复查
- 修正手机端过小、过糊或难以点击的角色和物件
- 为离线、更新失败和存档恢复制作状态插画
- 制作 PWA 安装引导图
- 制作测试版封面、分享图和反馈入口插画
- 完成图片响应式加载、压缩和缓存检查
- 检查所有动画的减少动态效果替代方案

### 核心验证指标

这些是产品判断指标，不是增长 KPI：

- 首次核心循环完成率 ≥ 70%
- 次日仍愿意回来使用 ≥ 35%
- 测试者中 ≥ 60% 能正确描述金币、精力、房间与入住的关系
- 测试者中 ≥ 50% 能说出至少一名喜欢或记得住的角色
- 严重存档丢失为 0

### 决策门

只有在以下两点同时成立时进入 1.0：

1. 完成现实待办确实会促使玩家回来；
2. NPC 和山谷成长确实比普通 Todo App 更有吸引力。

若第一点弱，优先改任务体验；若第二点弱，优先改角色内容和成长反馈，而不是增加更多货币或系统。

预计周期：根据 v0.9 测试结果决定

- 性能、离线和安装体验达标
- GitHub Pages 正式发布与版本说明

### 美术生产

- 从剩余角色中选择 3 人，按 v0.7 标准补齐完整角色素材
- 将临时剪影替换为正式山谷小人
- 补齐 6 名正式角色的事件插画和入住状态

- 清理所有占位素材和未使用的大文件
- 为正式素材建立版本清单，确保未来存档和界面升级可追踪

### 1.0 验收

- 设计文档 P0 项目全部完成并经过实际游玩验收
- 从首次打开到伴侣入住存在完整路径
- 连续使用 14 天不会耗尽主要内容
- 关键流程无阻断级错误

- 六名角色、房间与山谷的画风和光线保持一致
- 首次加载、离线缓存和版本更新不会因素材体积失控

## 4. 1.0 之后

以下内容先进入候选池，不在 MVP 阶段并行开发。

### P1：内容扩展（v1.x）

- 角色池从 6 人扩展到 12 人
- 长剧情、群像事件和节日事件
- 更多房间、装饰和礼物
- 标签与房间联动
- 更丰富的周/月回顾

### P2：小镇（v2.0）

- 山谷外地块
- 民居与店铺建设
- 镇民申请入住
- 繁荣度与远景变化
- 极轻量被动收益

必须保持规则锚点：

> 家里住人是伴侣，需要玩家维护；镇上住人是镇民，不消耗伴侣维护费。

## 5. 工作优先级

每个候选功能按以下顺序判断：

1. 是否加强“完成现实待办 → 获得情感或视觉反馈”？
2. 是否帮助玩家理解下一步？
3. 是否让角色更鲜活、山谷更有变化？
4. 是否降低存档丢失、错误或发布风险？
5. 新素材是否能复用已锁定的风格、构图或角色参考？
6. 是否只是增加系统或图片数量？

只满足最后一条的功能延后。

## 6. Issue 拆分约定

每个里程碑拆成可以独立验收的 GitHub Issue：

- 一个 Issue 尽量控制在 0.5–2 天
- 标明所属版本：`v0.5`、`v0.6` 等
- 标明类型：`feature`、`content`、`art`、`tech`、`bug`
- 必须写用户价值和验收条件
- 美术 Issue 必须写尺寸、格式、透明要求、页面用途和参考图
- 生成素材与接入界面可以拆成两个 Issue，但必须在同一里程碑完成
- 大功能先写设计 Issue，再拆实现 Issue
- 每个版本结束后进行一次真实设备试玩和回顾

建议先建立的八个 Issue：

1. 为核心规则建立测试框架和首批测试
2. 为本地存档增加版本号、迁移和损坏恢复
3. 建立视觉圣经、色板和图像 Prompt 模板
4. 生成山谷风格候选并锁定基准图
5. 制作沈渡、顾晚、桃桃的角色设定方向
6. 建立素材目录、压缩流程和登记表
7. 设计并实现四步首次引导
8. 设计“完成待办”的奖励动效与山谷反馈
